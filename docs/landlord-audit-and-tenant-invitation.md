# 房東功能檢查與租客邀請流程設計

檢查日期：2026-09-24。範圍：目前本機工作目錄，含尚未提交的新資料庫相容性修改。

本次為程式、路由、API、資料儲存及流程檢查；補做隔離資料庫重現與相關測試。沒有對正式資料進行新增、退租、收款或寄送邀請，也沒有宣稱已在瀏覽器逐一點擊全部按鈕。以下「建議」與邀請設計尚未實作。

## 結論

房務與租客基本管理已有後端資料與房東權限檢查，但整體還不是完整的雙端租務系統。財務、修繕、合約附件、續約與設定有多處停留在瀏覽器資料或示範操作。升級 ORM／資料表，以及現有單元測試通過，不能代表這些功能已串接完成。

目前沒有房東邀請租客加入租約的完整流程。LINE 模擬邀請、團隊成員邀請、共居邀請是不同用途，不能拿來替代租客與租約的正式綁定。

## 高優先問題與程式依據

### A. 跨帳號與跨裝置資料問題

- `src/composables/useRepairTickets.ts:117,414,466`：共用儲存鍵、預設示範工單、直接回傳全部工單；`src/pages/landlord/maintenance.vue:81` 的篩選只有畫面條件，沒有房東所有權條件。切換房東仍可看到同瀏覽器的案件，與後端 API 權限防護是兩回事。
- `src/composables/useLandlordFinance.ts:42`：收款與支出用全域 localStorage 鍵，支出未按房東隔離，跨裝置不可共用。
- `src/composables/useLandlordWorkspace.ts:21,37,55`：單例狀態未依帳號重置；請求失敗保留舊資料／ready 旗標，切換帳號時有舊資料殘留風險；固定取第一頁 100 筆。
- `src/composables/useLandlordSettings.ts:40,87`：儲存鍵雖按 email 區分，state 卻只在模組載入時讀取，換帳號未重新 hydrate，可能將前帳號狀態寫入後帳號鍵。

建議：所有正式資料由後端依帳號／工作區授權；前端快取按 user ID 區分，登入／登出時清除或切換，請求結果必須與發起帳號一致。

### B. 租約狀態不一致

- `backend/routers/landlord_properties.py:75`：只確認 end_date 未過期，没有要求 start_date 已到，且包含 pending，所以未起租也顯示 rented。
- `backend/routers/landlord_tenants.py:106`：選最新開始的租約，未優先選今天真正有效的租約，將來存在續約時可能蓋過目前租約。
- `_lease_display` 依日期顯示 occupied，但 `_is_effective` 要求 status=active。前端新增未來合約會存 pending，未找到到期自動轉 active 的機制。
- `backend/routers/landlord_tenants.py:345`：送出未來退租立即寫 ended/terminated；`_room_dict` 又將 turnover 映射為 vacant。
- `backend/routers/landlord_tenants.py:209`：重疊檢查將起訖兩端都視為包含。續約畫面預設開始日等於舊結束日；將來串接續約 API 時必須統一日期邊界規則。

建議：分開「預約／租約生效」、「實際入住」、「房間整備」與「帳款結清」。未起租不算入住；預定退租不立即釋出；退租後待整備不等於可出租。選擇一致的起訖日語意並套用於所有頁面。

### C. 畫面成功不等於完成

- `src/pages/landlord/contracts.vue:203`：續約只是 unshift 至記憶體；`:210` 上傳附件只取 file.name。
- `src/pages/landlord/contracts.vue:154`：編輯提交只有租期、租金、押金、繳租日與編號，其他可編輯欄位未保存。
- `src/pages/landlord/contracts.vue:47`：空資料時 selected 為 undefined；template 詳情直接用 selected.state 等屬性，缺少 v-if／空狀態保護（程式確認，未做瀏覽器重現）。
- `src/composables/useLandlordFinance.ts:172` 及 `src/pages/landlord/finance.vue:111`：沒有通知 API 卻顯示「已發送提醒」。
- `src/components/landlord/RentalCenterPopover.vue:31`：通知資料為固定 tasks。

建議：只有後端確認成功才呈現完成。未串接者應明示示範／未啟用；新增續約及附件要有可再次查到的後端紀錄。

### D. 帳務資料不完整

- 本月租金由當下租約重算，修改租金可能改變既有期帳金額；已終止租約會退出 activeTenants，未結清款項可能從視圖消失。
- 部分收款與逾期應為兩個維度；目前 partial 優先使逾期餘額不列入 overdue。
- 租約中途起訖、季繳最後不足三個月、押金扣抵、退租結算、溢付／退款規則尚未成為帳單流程。
- 新 `bills` 連到 `rentals`，房東頁主要操作 `landlord_leases`。兩套租約資料尚無明確關聯，不能只把財務前端換成 bills 查詢就當成串接完成。

建議：建立固定的期帳及獨立收退款紀錄，保留租約／租客外鍵、期起訖與調整歷史。先確立 `rentals` 與 `landlord_leases` 的對照，再接帳單、修繕及租客畫面。

## 房東邀請租客：目前與目標

目前 `backend/routers/tenant_leases.py:25` 以 `LandlordTenant.email == current_user.email` 顯示租約，沒有明確的使用者 ID 綁定與接受紀錄。房東填錯 email、租客換 email、未填 email 都會造成問題；它也不是租客確認接受邀請的流程。

目標：一份邀請指向房東名下的具體租約／租客資料，QR code、連結、邀請碼只是三種入口，最終執行同一個「租客確認並綁定」動作。

### 使用流程

1. 房東註冊房東帳號，建立棟別、房間、租客聯絡資料與租約。租客尚未註冊不影響房東先管理物件。
2. 租客詳情／租約詳情新增「邀請加入」；房東確認對應房間及租期，選擇指定租客 email。尚不知 email 時，接受後須經房東確認，不能讓持碼者直接取得資料。
3. 系統建立一筆邀請，同時提供 QR code、複製連結及手動邀請碼。QR code 使用相同邀請網址，不能只是房號或 tenant ID；複製成功只代表已複製，不代表已送達。
4. 租客掃描／點連結進入公開邀請頁，只顯示必要且適度遮罩的房東／物件／租期概要，不展示證件、完整聯絡資料或帳款。
5. 已有租客帳號：登入後回到邀請確認頁。沒有租客帳號：以 tenant 註冊、完成 email 驗證後回到相同邀請；Google 登入也保留邀請上下文。
6. 直接從註冊頁進入者可填選用的「房東邀請碼」；欄位僅在租客註冊顯示。已有帳號者在「加入租約」也能輸入碼，不必重新註冊。
7. 如果目前登入的是房東帳號，提示登入或註冊租客帳號。同 email 允許另一個 tenant 帳號，但不能把原 landlord 帳號變成雙角色，也不能建立第二個 tenant 帳號。
8. 驗證符合指定收件人、邀請仍有效、租約沒有被撤銷／綁定後，顯示確認頁，由租客按「確認加入」。單純 GET 預覽不可消耗邀請。
9. 在同一資料庫交易內建立 user ID 與租約的綁定、記錄接受時間並消耗邀請。房東顯示「已加入」，租客看到自己的房間、租約及已串接的功能。
10. 同一使用者重送接受請求回傳既有成功結果；另一位使用者搶先／重複接受必須失敗。重新整理、重試與不同裝置都不能生成重複帳號或重複綁定。

### 狀態與例外

| 情況 | 預期行為 |
| --- | --- |
| 已指定 email，登入信箱不同 | 不自動綁定；提示換租客帳號或請房東重發，不顯示敏感資料 |
| 未指定 email | 驗證帳號後提出加入申請，房東確認身分後才開放資料 |
| 邀請過期、撤銷、房東重發 | 拒絕接受；重發使舊邀請失效 |
| 已由本人接受 | 顯示已加入並前往該租約 |
| 已由別人接受 | 不覆蓋原綁定；交房東處理 |
| 房東帳號或租約停用／終止 | 拒絕新接受；歷史資料權限按既定保留規則處理 |
| 同租客有多段／多房東租約 | 仍使用同一 tenant 帳號，透過不同租約綁定，不重建帳號 |
| 換租客／退租 | 結束該段租約的有效權限；新租客用新租約邀請，不覆寫舊人歷史 |
| 驗證碼輸入失敗、登入取消、跨 Google 回呼 | 邀請保持未消耗；登入流程完成後仍可繼續 |
| 邀請碼錯誤但一般註冊成功 | 帳號可存在；加入租約另行處理，不把帳號註冊與租約綁定混成不可恢復的半成品 |

建議邀請有效期預設 7 天，房東可撤銷／重發；這是待實作的產品預設，不是目前已有功能。

### 必要資料與 API（設計草案）

需正式新增 migration，同時維護 MySQL 定義、ORM、SQLite 升級及測試，不能復用 `households.invite_code`。

- 邀請表：房東 ID、租客聯絡紀錄 ID、租約 ID、指定 email（可空）、隨機 token／手動碼的雜湊、到期時間、狀態、接受者 ID、接受／撤銷時間。角色固定 tenant，不能信任前端傳來的角色。
- 租約帳號綁定：租約 ID、tenant user ID、接受與終止時間；目前單租客模型下一份有效租約只能有一個有效主要租客帳號，但同帳號可有多份租約。更換綁定保留稽核歷史。
- 房東 API：建立、查詢狀態、撤銷／重發；每次都檢查房東所有權。
- 公開 API：限縮資訊的邀請預覽／碼驗證；長 token 採安全隨機值，短碼需限流及嘗試次數限制。
- 租客 API：確認接受、查詢已綁定租約；驗證 tenant 角色及 email 驗證狀態，以交易／鎖與唯一限制避免同時搶領。
- 通知：綁定成功、撤銷等可另建真實通知；LINE 屬選配通知通道，不是加入系統的必要條件。
- QR code 本機產生，避免把邀請 token 傳给第三方 QR 服務。掃碼使用手機可達的正式 HTTPS 網址；localhost:5173 在手機上不會指向房東電腦。

email 作為指定收件人的驗證條件，正式授權依 user ID＋租約綁定。既有「只靠同 email 顯示租約」應過渡至經確認的綁定；既有帳號不可在無確認的情況下盲目自動認領。

### 驗收清單

- QR、連結、手動碼都導向同一份租約，email／Google 註冊後不丟失上下文。
- 新租客、既有租客、同 email 房東另建租客、登入錯角色皆能正確引導。
- 過期、撤銷、重發、重放、雙人同時接受、錯信箱、非本人房東操作均有測試。
- 綁定後，房東電腦與租客手機讀到同一份後端租約；其他房東／租客不可查到。
- 接受邀請不改租金、租期或入住狀態，不代表簽署法律合約或完成入住點交。
- 註冊可不帶邀請；已有帳號可事後加入；租客帳號與租約數量分開處理。
- 房東先行使用時可管理租約與帳款，租客加入後是取得對應權限，不再建立第二套互不相連的租約。

## 建議實作順序

1. 先排除跨帳號殘留、空合約畫面、續約假成功、附件假上傳、催繳假通知及未來退租立即生效等高影響問題。
2. 統一租約有效期／房間狀態，建立明確的租約與 tenant user ID 綁定，以及 rentals／landlord_leases 的資料對照。
3. 完成邀請表、接受 API，再接 QR／連結／手動碼與登入註冊回跳。
4. 財務改為持久化期帳與收退款紀錄；修繕改後端工單與檔案，最後接通知、團隊權限及真實訂閱。
5. 使用兩個房東帳號、兩個租客帳號和兩部裝置做完整驗收，重點覆蓋邀請 → 入住 → 帳單／報修 → 續約／退租。
