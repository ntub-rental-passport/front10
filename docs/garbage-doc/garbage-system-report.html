RentMate 臺北市／新北市垃圾清運查詢系統報告書

文件日期：2026-09-11　｜　程式基準：d7477f1　｜　用途：專題系統說明、後端與資料庫交接

本報告依目前儲存庫程式與本地資料快照整理。文中「已實作」表示程式具備該能力，不代表正式環境的憑證、GPS 來源、通知或排程已驗收。外部資料來源連結來自專案內的來源紀錄，本次未重新查核官網資料。

1. 系統定位與交接摘要

本功能整合臺北市、新北市清運班表，讓使用者以地圖、條件列表、GPS 或手動選點找到清運站點，查看各類清運班次與下一班倒數，並使用收藏及到達前提醒。

目前的核心是「官方表定班表查詢」，不是已完成的即時車輛追蹤或 ETA 預測系統。介面「營運中」「即將抵達」依班表時間判定，不是由車輛到站事件決定。

交接重點現況後端／資料庫成員需要知道的事
頁面入口/app/garbage；/garbage 重新導向前者共用既有登入、導覽、維護開關
站點與班表前端直接讀取 public/data 靜態檔案目前沒有站點查詢 REST API，也沒有清運站點 ORM 資料表
收藏依帳號區分的瀏覽器 localStorage未存進後端，無跨裝置同步
個人 GPS／手動選點僅在前端記憶體使用現有清運 API 不上傳使用者查詢位置
車輛 GPS臺北市有可設定的代理介面；新北市尚未串接需另取得合法可用來源並轉換欄位；不能把手機 GPS 當成車輛 GPS

路線圖官方站序／表定時間排序後的霓虹實線是站點連線示意，不是沿道路導航或實測車輛軌跡

2. 頁面功能與操作流程

2.1 共用介面

桌面版將標題、七個功能分頁、縣市選擇整合成水平一列，縣市選擇位於最右側；頁首會隨捲動保持可見。窄螢幕將功能分頁另列，允許水平捲動。標題副標與班表時鐘已移除，但內部時鐘仍持續計算倒數及狀態。

功能分頁操作與結果資料來源／依賴
地圖查詢地圖左上「查詢條件」開啟彈窗；篩選行政區、里、道路、日期與時段；點選站點查看詳情靜態班表、MapLibre、OpenFreeMap
列表查詢左側條件欄、站點列表、每頁 20 筆；地址字體 16px；可開啟每週班表前端篩選、分頁；不顯示附近動態看板
附近查詢啟用 GPS；半徑可選 100、200、300、400、500 公尺，預設 500；按直線距離排序瀏覽器定位；不顯示附近動態看板
手動定位點擊地圖指定中心，以半徑 200 公尺找站點；再點選即更新不需要 GPS；看板與結果都以手動位置為中心
我的收藏星號加入／取消收藏；依目前縣市顯示本機 localStorage，不等於後端收藏資料
提醒設定選站點、日期、提前分鐘及通知方式；檢視啟用與傳送狀態FastAPI、SQLite、SMTP／Web Push
操作指引說明查詢、定位、路線、收藏、提醒與資料限制說明元件

2.2 附近清運地點看板與快速篩選

看板位於地圖上方；順序是「看板 → 單列快速篩選 → 地圖」。目前看板出現在地圖、手動定位與收藏模式；列表及附近模式不顯示。以目前查詢中心找出附近實體地點，去除重複地點後最多顯示三張卡片；部分螢幕寬度會隱藏第三張卡。

地圖／收藏看板使用 GPS 中心的 500 公尺範圍；手動看板使用手動中心的 200 公尺範圍。卡片提供今日表定班次、下一班倒數、下一班日期時間、三類清運資料、距離、收藏與每週班表入口。

快速篩選有「全部站點、現在、10 分內、30 分內、1 小時內抵達」。選擇快速篩選會把查詢日期切回今天，清空自訂起迄時間。「30 分內」可以包含尚未進入黃色 15 分鐘提示的站點；篩選範圍與狀態顏色是不同規則。

2.3 STOP DETAILS 站點資訊卡

由地圖或站點地址開啟。上方保留地址、行政區／里別／清運單位、狀態標籤與大字時間；主要資訊改成下列三列：

欄位顯示與規則
表定抵達抵達時間旁附剩餘小時／分鐘；跨服務日標示「下一班」；倒數不是 ETA
離站時間臺北顯示「表定離站」；新北顯示「估計離站」
路線名稱可點擊，關閉站點卡並開啟該完整班次路線卡

下方仍可展開垃圾／回收／廚餘班表、回報資料問題、收藏與設定提醒。原有長段估算及準誤點說明已從卡片移除；估計離站的資料旗標及底層邏輯仍保留。

2.4 清運班次路線

支援搜尋路線名稱、行政區、車號、地址。路線使用目前城市完整班表分組，不因附近半徑或目前站點篩選而截短。分組鍵包含城市、行政區、路線 ID／名稱、清運單位、車牌、車次，避免同名不同車次串接在一起。

有官方 rank 時依站序排列；其餘依抵達時間及 ID 排序。列表顯示 1、2、3…，地圖對應相同編號；無效座標仍保留列表位置，不繪點，線段在缺少座標處斷開。

地圖使用三層藍色霓虹實線：外層模糊光暈、藍色主線、亮色細線。卡片可拖曳標題區移動，也可用方向鍵調整，移動範圍限制在地圖容器內。

顯示路線保留目前選取恢復

5. 資料字典與計算規則

5.1 本地資料快照

城市檔案班次記錄數行政區來源紀錄
臺北市taipei-garbage.csv4,01012匯入 2026-09-08；metadata 記錄來源更新 2026-08-25T16:33:23+08:00
新北市new-taipei-garbage.json26,65529匯入 2026-09-10T10:39:52.186Z；來源更新時間為 null

數量是班表停靠記錄，不是去重後的實體站點，也不是車輛數。臺北既有資料檢核記錄有 9 筆無效座標、3 筆 24:xx 跨日記錄；新北 metadata 記錄無效座標為 0。正式匯入仍應重新跑驗證，不能把這些數量當成永遠固定的規格。

collections.days 前端使用 JavaScript 星期編碼：0＝星期日、1＝星期一…6＝星期六。後端 Python weekday() 則為 0＝星期一…6＝星期日；新北後端解析已做自己的轉換，資料庫整合必須明確指定同一編碼。

臺北 ID：行政區|里別|路線|車次|地點|抵達時間，使用原始欄位清理後組合。新北 ID：ntpc|lineid|rank|latitude|longitude，座標片段保留來源字串。不要只以地址去重，也不要把 ID 中座標重新格式化；班表更新、站序或座標變動可能造成 ID 改變，需規劃舊 ID 對照。

6. 現有 API 契約

開發環境由 Vite 將 /api 代理至 FastAPI，預設 http://127.0.0.1:8000。正式前端以 VITE_API_BASE_URL 或 /api 組合路徑。garbageRequest 逾時 15 秒，會附上現有 session 的 Authorization: Bearer <accessToken>。

Method路徑身分回應／用途
GET/api/garbage/capabilities公開{email, push, publicKey}，控制可用通知方式
GET/api/garbage/vehicles公開{status, message, vehicles}，目前只供臺北來源
GET/api/garbage/reminders正式租客自己的提醒陣列，依 due 遞減
POST/api/garbage/reminders正式租客建立提醒，成功 HTTP 201
PATCH/api/garbage/reminders/{id}正式租客body {active: boolean}，成功 {ok: true}
DELETE/api/garbage/reminders/{id}正式租客刪除自己提醒，成功 {ok: true}

站點、路線、收藏、問題回報都沒有對應的現有後端 CRUD API。回報功能只組成 GitHub Issue 草稿連結，最後由使用者自行送出。

6.1 建立提醒

以下為欄位示例，stationId 必須取自同版本班表，示例日期不表示可直接在任意日期測試成功。

{
  "stationId": "<目前班表中的完整 ID>",
  "date": "2026-09-12",
  "minutesBefore": 15,
  "notifyPush": false,
  "notifyEmail": true
}

選擇推播時另帶 subscription: {endpoint, keys: {p256dh, auth}}。目前前端 ReminderInput 型別未列 subscription，但頁面送出 payload 與後端模型支援該欄位，正式 API 文件與型別整合時應補齊。

後端驗證站點存在、服務日合法、提前時間 1～120 分鐘、due 在未來且不超過現在 366 天、至少一種通知方式及通道已設定。每帳號最多 50 筆啟用且未到期提醒。收件信箱由租客帳號取得，不接受前端自由指定。

提醒回應欄位包含 id, stationId, stationName, date, arrival, minutesBefore, notifyPush, notifyEmail, active, dueAt, emailStatus, pushStatus。recipient 與 subscription 不會回傳前端。

輸入驗證錯誤為 HTTP 422；找不到本人提醒為 404；身分驗證交由既有 get_current_tenant。前端只直接顯示字串型 detail，Pydantic 陣列錯誤目前會落到通用錯誤提示。

6.2 車輛定位

標準化來源需回傳下列結構，這是本系統要求的 adapter 格式，不是保證官網原生 API 就有的格式：

{
  "vehicles": [
    {"plate": "821-BT", "lat": 25.11836, "lng": 121.525, "updatedAt": "2026-09-11T18:30:00+08:00"}
  ]
}

後端來源請求逾時 8 秒、快取 20 秒；前端每 30 秒刷新。後端接受臺北座標範圍與帶時區時間戳，排除超過 120 秒、或未來超過 30 秒的車輛。status 可為 unconfigured、live、stale、unavailable。新北模式直接清空車輛陣列，不使用臺北 API 冒充新北即時資料。

現有表沒有 created_at、updated_at、重試次數、provider message ID、外鍵、去重鍵或訂閱獨立表。這些不是已完成能力。

7.3 通知生命週期

未選通道 → disabled
已選通道 → pending → 原子領取 sending → sent / failed
pending 超過應發送時間 5 分鐘 → missed
active=0 → 排程略過

每 20 秒檢查，每通道每輪最多取 50 筆；以條件 UPDATE 將 pending 改為 sending，避免共用同一 SQLite 的 worker 同時領取。程式中斷可能留在 sending，需要人工確認，沒有自動重試。這不是端到端 exactly-once 保證；SMTP 成功只代表寄送呼叫成功，不保證送達收件匣。

提醒保存建立時的班表快照。更新政府資料不會自動重算已排程提醒；後端 stops() 有 lru_cache，資料更新後需重啟服務。
