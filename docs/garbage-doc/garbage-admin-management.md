# 垃圾清運系統：後台管理需求與交接說明

文件日期：2026-09-11  
適用對象：後台管理員、後台前端開發、後端開發、資料庫開發成員  
文件性質：後台管理功能規劃，非已完成實作清單

## 1. 目的與現況

垃圾清運前台已提供臺北市／新北市地圖、列表、附近查詢、手動定位、路線、收藏及表定提醒。後台需要協助維護資料品質、處理回報、查明提醒發送問題，並保留可追溯的操作紀錄。

目前垃圾清運資料分散於以下位置，不能直接視為已接入管理後台：

| 資料 | 目前儲存／處理方式 | 後台整合狀態 |
| --- | --- | --- |
| 站點、路線、班表 | `public/data` CSV／JSON 快照，前後端分別解析 | 尚無專用管理 API 或清運站點資料表 |
| 收藏 | 依帳號區分的瀏覽器 localStorage | 未上傳後端，無跨裝置同步 |
| 使用者 GPS／手動查詢中心 | 前端記憶體 | 現有清運 API 不接收查詢座標 |
| 個人提醒 | FastAPI＋獨立 SQLite `garbage_reminders` | 已有租客端 CRUD，尚無專用管理員介面 |
| Email／Web Push | 後端排程與傳送程式 | 需正式設定及實際驗收；未自動整合後台通知管理 |
| 問題回報 | 產生 GitHub Issue 草稿，使用者自行送出 | 尚無站內回報工單資料表 |
| 真實車輛 GPS／ETA | 臺北有可設定來源的代理介面；新北尚待串接 | 不應把表定狀態當作即時到站紀錄 |

參考的[後台管理系統功能總覽](../後台管理系統-功能總覽.md)更新於 2026-07-29，其中包含三種角色及 localStorage／模擬通知等當時設計。現行 [admin-rbac.ts](../../src/utils/admin-rbac.ts) 已使用「超級管理員、一般管理員」兩種角色。本規劃以現行角色為基礎；引用舊文件的操作原則，不將其描述直接當成目前全部模組的實作現況。

## 2. 管理原則

1. **官方原始資料與管理員修正分開保存。** 保留原始快照及修正覆蓋層，避免下一次更新覆蓋人工查核結果。
2. **重要異動先存草稿，再確認生效。** 發布班表、回復版本、變更計算參數或批次影響提醒前，應呈現變更內容與影響筆數。
3. **異動必須可追溯。** 紀錄操作者、時間、對象、前後差異、原因與結果。
4. **資料版本、系統執行紀錄、管理員稽核分開。** 三者用版本 ID、批次 ID、提醒 ID 等欄位串接。
5. **不以畫面標籤代替真實結果。** 新增一筆通知紀錄，不等於 SMTP／推播已成功發送；表定營運中，不等於車輛已確認到站。
6. **管理權限由後端驗證。** 隱藏側邊欄或按鈕只是介面控制，API 仍須檢查角色與動作權限。
7. **只存業務必要資料。** 不預設保存使用者精確 GPS、完整查詢軌跡或私人收藏明細。

建議在「營運管理」新增「垃圾清運管理」，規劃路徑 `/admin/garbage`。這是建議路徑，尚未建立。

## 4. 各類資料的存取需求

### 4.1 站點、路線與班表

**需要查看的資料**

- 城市、行政區、里別、地址、經緯度、座標有效性。
- 來源站點 ID、來源版本、路線 ID／名稱、車號、車次、清運單位。
- 官方站序或時間排序依據。
- 垃圾、回收、廚餘各自收運日及抵達／離站時間。
- 離站是否估計、原始值、修正值、前台目前採用的值。

**建議操作**

一般管理員可以查詢、檢查異常、提出修正草稿與停用申請。超級管理員核准發布、停用及恢復。停用優先於直接刪除，避免收藏或提醒失去對應。

每次修正應保存欄位名稱、原始值、新值、原因、證據來源、申請人、核准人、生效與失效時間。對地址、座標、站序的修改，不應任意重建或格式化舊 ID。

### 4.2 資料更新與版本

| 必備資料 | 用途 |
| --- | --- |
| 城市、資料集版本、來源 URL、checksum | 確認來源與內容版本 |
| 抓取時間、來源更新時間、發布時間 | 區分檢查時間與官方內容更新時間 |
| 總筆數、行政區數、新增／刪除／異動數 | 判斷更新影響 |
| 欄位、座標、時間、重複 ID 等檢核結果 | 防止錯誤資料直接上線 |
| 目前前台版本、後端班表版本 | 發現兩端資料不一致 |
| 發布／失敗／回復狀態及執行人 | 追蹤發布結果 |

建議流程：執行更新檢查 → 保存候選版本 → 查看差異與異常 → 核准發布 → 同步前後端 → 驗證成功。回復舊版本也需確認影響及留下紀錄。

目前前後端使用同一套快照檔案，後端另有班表快取；正式發布流程需處理後端快取刷新。既有提醒保存建立時班表，不會自動因新版本而重排。

### 4.3 臨時停收與班表異動

管理資料應包含官方來源、公告內容、城市、影響路線／站點、服務日期、開始／結束時間、異動類型及發布狀態。

公告文字與班表例外資料要分開：只發布「今天停收」的文字，不會自動讓提醒停止發送。若要影響查詢或提醒，需要後端明確處理班表例外。

發布前列出影響的班次與待發送提醒數，並選擇明確政策，例如取消受影響提醒、要求使用者重設、或經確認重排。保存採用政策與執行結果。

### 4.4 使用者問題回報

| 欄位 | 建議內容 |
| --- | --- |
| report_id | 回報識別碼 |
| category | 地址／座標／時間／路線／操作問題 |
| station_id、route_id、city | 對應資料；未指定時可留空 |
| description、observed_at | 使用者描述與觀察時間 |
| source_url | GitHub Issue 或查核證據連結 |
| assignee_id、status | 處理人及狀態 |
| resolution、resolved_version | 處理結果及實際修正版本 |

建議狀態：待處理 → 處理中 → 待補資料／待發布 → 已解決；不採納時必須填理由。

初期可以保留既有 GitHub 回報方式，由管理員登記連結；若要同步 Issue 狀態，需額外建立整合，不能只靠前端草稿連結達成。

### 4.5 提醒與通知發送

管理員需查看提醒 ID、使用者 ID、遮罩後收件資訊、站點、服務日期、表定抵達、應發送時間、通道、啟用狀態、實際傳送結果及錯誤原因。

| 操作 | 建議限制 |
| --- | --- |
| 查詢提醒與失敗紀錄 | 一般管理員可查業務必要欄位 |
| 查看完整收件資料 | 另授權，並記錄敏感存取 |
| 取消失效提醒 | 需權限、理由及影響預覽 |
| 補發／重試 | 超級管理員或明確授權者執行；確認未過期及是否可能重複發送 |
| 批次取消／補發 | 需二次確認、筆數限制與批次紀錄 |
| 修改傳送結果 | 不提供任意改成「成功」的功能；結果由系統回寫 |

目前清運提醒有 `pending`、`sending`、`sent`、`failed`、`missed`、`disabled` 等通道狀態。`sending` 可能代表程序中斷後結果未確認，不宜直接自動補發。Email `sent` 表示寄送呼叫成功，不代表使用者已收到或已讀。

現有 `garbage_reminders` 只有每通道目前狀態，沒有逐次嘗試歷程。重試次數、provider message ID、完整失敗分類與管理員補發仍需新增資料及 API。

### 4.6 系統監控與參數

監控建議呈現資料來源最後成功時間、GPS 資料新鮮度、API 錯誤率、排程器最後執行時間、待送佇列數、超時提醒數、SMTP／推播傳送失敗數。

設定建議包含「即將抵達」門檻（目前 15 分鐘）、新北估計停留時間（目前 10 分鐘）、查詢半徑選項及提醒數量限制。這些目前分散於程式，加入後台設定需要同步前後端計算規則。

變更設定時必須說明是否影響既有提醒。不得讓前端已改成新門檻、後端仍使用舊設定，卻沒有版本或生效時間可查。

## 5. 權限配置建議

以下是新增清運功能的建議權限，尚未加入現有 RBAC。

| 操作 | 一般管理員 | 超級管理員 |
| --- | --- | --- |
| 查看站點、路線、版本、監控 | 可 | 可 |
| 處理回報、建立修正草稿 | 可 | 可 |
| 執行資料抓取與驗證，不發布 | 可，需限制頻率 | 可 |
| 發布修正、停用／恢復站點、回復版本 | 不可，提交核准 | 可 |
| 查看遮罩後提醒及傳送結果 | 可 | 可 |
| 查看完整收件資訊／匯出明細 | 預設不可 | 具業務需要時可，記錄存取 |
| 批次取消／補發提醒 | 預設不可 | 可，需確認及紀錄 |
| 修改清運系統參數 | 不可 | 可 |
| 查看完整統一稽核紀錄 | 不可 | 可 |

後端應以動作區分讀取、修正草稿、發布、設定、補發及匯出權限。管理員 API 與現有租客提醒 API 必須區隔，不能直接放寬租客端查詢條件來達成管理功能。

## 6. 必須保留的三類紀錄

| 類型 | 記錄內容 | 範例 |
| --- | --- | --- |
| 資料版本紀錄 | 原始快照、檢核、差異、發布／回復結果 | 新北版本 A 升為 B，修改 35 筆 |
| 系統執行紀錄 | 抓取、排程、API、每次通知傳送 | 18:12 發送失敗，SMTP 逾時 |
| 管理員稽核紀錄 | 管理員異動及敏感存取 | 核准某站座標修正，取消某批提醒 |

### 6.1 管理員稽核欄位

| 欄位 | 說明 |
| --- | --- |
| event_id | 唯一事件識別碼 |
| actor_id、actor_role | 操作者及操作當下角色；自動作業使用系統身分 |
| occurred_at | 帶明確時區的事件時間 |
| action | 動作，例如修正、發布、回復、取消、補發、匯出 |
| target_type、target_id | 站點、版本、提醒、設定等目標 |
| before、after | 實際變更欄位與前後值；不保存密碼或完整訂閱 |
| reason | 人工變更或特殊處理的原因 |
| result、error_code | 成功／失敗及可查詢的錯誤分類 |
| request_id／batch_id／version_id | 關聯 API、批次作業與資料版本 |

一般列表查詢不必每次寫成異動稽核；查看完整收件資訊、匯出個人資料、補發通知等操作應留下存取紀錄。稽核不得提供一般編輯／刪除介面；保留期限與清理權限需由團隊訂定。

### 6.2 建議事件名稱

```text
garbage.dataset.checked
garbage.dataset.published
garbage.dataset.rolled_back
garbage.stop.correction_submitted
garbage.stop.correction_approved
garbage.stop.disabled
garbage.stop.restored
garbage.service_exception.published
garbage.report.assigned
garbage.report.resolved
garbage.reminder.cancelled
garbage.reminder.resend_requested
garbage.settings.updated
garbage.recipient.revealed
garbage.records.exported
```

事件名稱是建議契約，正式實作時應對齊既有稽核資料格式，不另建與全站無法串接的格式。

## 7. 資料庫整合建議

現有清運提醒 SQLite schema 只有 `id、user_id、payload、due、active、email_status、push_status`。其餘以下資料表為提案，尚未建立。

| 建議資料表／共用資源 | 用途 | 關鍵關聯 |
| --- | --- | --- |
| garbage_dataset_versions | 來源快照版本與發布狀態 | city、checksum、published_by |
| garbage_import_runs | 抓取及檢核執行結果 | version_id、batch_id |
| garbage_stops／routes／route_stops／schedules | 正式站點、路線、站序與分類班表 | 保留來源 ID、服務日與版本 |
| garbage_data_overrides | 人工修正覆蓋層 | station／route_stop、原始版本、核准人、有效期間 |
| garbage_service_exceptions | 臨時停收或改時 | 日期、適用城市／路線／站點 |
| garbage_reports | 資料問題工單 | 站點、處理人、來源連結、修正版本 |
| garbage_reminders | 個人提醒主檔，擴充或遷移既有表 | user_id、站點、班表快照、due_at |
| garbage_notification_deliveries | 每通道、每次傳送嘗試 | reminder_id、attempt、provider ID、result |
| 共用 settings／announcements | 清運參數與對外公告 | 版本、生效時間、適用範圍 |
| 共用 audit_logs | 管理異動與敏感存取 | actor、target、request／batch／version |

資料庫設計注意事項：

- 原始班表、人工覆蓋、前台採用結果要能互相追溯。
- 同一地址可能有多條路線與多個班次，不能只以地址設唯一鍵。
- 24:xx 是服務日延伸到隔日的時間，需保留服務日與分鐘偏移。
- 星期編碼必須統一：前端 JavaScript 與後端 Python 的 weekday 定義不同。
- 刪除／停用站點或發布新班表前，先檢查受影響提醒與收藏 ID。
- 通知主檔與傳送嘗試分開保存；每次重試應有新嘗試紀錄及去重機制。
- 若遷入共用 DB，須規劃舊 SQLite 提醒的遷移、擁有者關聯及未完成傳送狀態。

## 8. 管理員 API 規劃方向

以下路徑僅作討論草案，不是現有 API：

| 能力 | 建議路徑 |
| --- | --- |
| 站點／路線查詢 | `GET /api/admin/garbage/stops`、`GET /api/admin/garbage/routes` |
| 提交修正、核准 | `POST /api/admin/garbage/corrections`、`POST /api/admin/garbage/corrections/{id}/approve` |
| 更新檢查與發布 | `POST /api/admin/garbage/imports`、`POST /api/admin/garbage/versions/{id}/publish` |
| 回報查詢與處理 | `GET /api/admin/garbage/reports`、`PATCH /api/admin/garbage/reports/{id}` |
| 提醒與傳送紀錄查詢 | `GET /api/admin/garbage/reminders`、`GET /api/admin/garbage/deliveries` |
| 取消／申請補發 | `POST /api/admin/garbage/reminders/{id}/cancel`、`POST /api/admin/garbage/reminders/{id}/resend` |

各 API 需定義分頁、城市與日期篩選、動作權限、錯誤碼、操作者與稽核事件。批次或不可重複的操作要有請求去重／冪等機制。設定、公告、監控與稽核應優先沿用既有 API 契約。

## 9. 不建議預設蒐集或公開的資料

| 資料 | 建議處理 |
| --- | --- |
| 使用者精確 GPS／完整移動軌跡 | 清運查詢不需預設上傳或長期保存 |
| 私人收藏清單 | 不作為一般管理員日常瀏覽資料；統計以彙總為主 |
| 收件信箱 | 一般列表遮罩，完整查看另授權及留紀錄 |
| Push endpoint／auth 金鑰 | 不完整顯示於管理列表或稽核內容 |
| SMTP 密碼／VAPID 私鑰／登入 token | 只保存在受控後端設定，不寫入回應、匯出或稽核 |

使用分析可先收集每日查詢量、城市、查詢模式、錯誤率等彙總指標。資料保留期限、匯出權限及清理作業應在正式部署前訂定，不預設永久保存所有紀錄。

- [ ] 修正草稿、核准、有效期間與人工覆蓋層。
- [ ] 更新差異預覽、發布及版本回復。
- [ ] 臨時停收／改時與提醒影響預覽。
- [ ] 取消、補發及逐次傳送紀錄。
- [ ] 清運參數設定與版本同步。

### 第三階段：即時整合與分析

- [ ] 新北與臺北真實 GPS adapter、車輛與班次對應。
- [ ] 到離站事件及真實下一站／下下站判定。
- [ ] 有可靠資料後才加入 ETA 與準誤點分析。
- [ ] 資料品質趨勢、彙總使用量及通知可靠度分析。

## 11. 驗收情境

| 情境 | 預期結果 |
| --- | --- |
| 一般管理員直接呼叫發布 API | 後端拒絕，不只是隱藏發布按鈕 |
| 修正座標但未核准 | 前台仍用目前已發布資料 |
| 核准修正後再次匯入官方資料 | 人工修正仍可追溯，並提示衝突或已由官方修正 |
| 更新後前後端班表版本不一致 | 可發現異常並阻止或回復不完整發布 |
| 發布停收公告 | 顯示影響範圍；只有啟用班表例外處理才會同步影響提醒 |
| 點擊補發兩次 | 不產生未受控的重複發送 |
| 傳送中途程序中斷 | 不把未確認結果直接當作成功或安全可重試 |
| 查看完整收件資料／匯出 | 檢查權限並留下存取紀錄 |
| 修改參數 | 有前後值、理由、版本及生效時間，兩端規則一致 |
| 按取消或放棄草稿 | 不變更已發布資料，也不產生虛假的成功異動紀錄 |

## 12. 會議決策與相關文件

需要後台、後端、資料庫成員共同確認：

1. 第一階段是否只做查詢、回報及紀錄，第二階段才開放資料發布。
2. 提醒留在持久化 SQLite，或遷到團隊共用資料庫。
3. 資料修正、版本發布、取消與補發由誰核准。
4. 現有公告、通知、稽核與設定哪些已接後端，哪些仍是前端示範資料。
5. 班表異動對既有提醒採保留、取消或重排政策。
6. 誰負責正式通知、GPS 憑證及端到端驗收。
