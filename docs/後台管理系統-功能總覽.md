## 二、模組一:系統設定 + 維護模式

### 解決的問題
平台參數(檔案大小上限、AI 配額等)原本寫死在程式碼中,要調整就必須改程式並重新部署。

### 功能

**後台「系統設定」頁**,六項可調參數:

| 參數 | 說明 | 驗證規則 |
|------|------|---------|
| 網站名稱 | 顯示於平台各處 | 必填 |
| 客服信箱 | 對外聯絡窗口 | Email 格式 |
| 維護模式 | 全站開關 | — |
| 維護說明文字 | 維護頁顯示內容 | 開啟維護時必填 |
| 單檔上傳上限 | MB | 1–50 |
| 每日 AI 配額 | 次數 | ≧ 0 |

**操作特性**
- 採「草稿 + 確認」模式:修改後需按「儲存變更」→ 再於確認對話框按「**確認儲存**」才生效
- 開啟維護模式時,確認框會額外顯示警示,提醒管理後台不受影響
- 未修改時儲存鈕為停用狀態;驗證未通過時無法儲存
- 可「還原變更」放棄草稿
- 每次儲存都寫入稽核紀錄(含變更了哪些欄位)

### 連動點:維護模式
開啟後,**一般使用者不論訪問哪個網址,都會被路由守衛導向 `/maintenance` 維護頁**,顯示自訂的維護說明。管理員仍可正常進入 `/admin` 後台關閉它,避免把自己鎖在門外。

### 技術核心
`validateSettings()` 純驗證函式(**16 個測試**),將「什麼算合法設定」從畫面邏輯抽離,可獨立測試。

## 三、模組二:內容管理 + 公告

### 解決的問題
公告、常見問題、服務條款這類會頻繁變動的文字內容,原本散落在各頁面的程式碼裡。

### 功能

**後台「內容管理」頁**,四個分頁:

#### 1. 公告
- 新增 / 編輯 / 刪除(刪除有二次確認)
- **三種等級**:一般(藍)、注意(琥珀)、緊急(紅),前台以不同顏色與圖示呈現
- 發布狀態開關
- **生效期間**:設定開始日與結束日(結束日可留空 = 長期有效)

#### 2. 常見問題(FAQ)
- 依四個分類自動分組:租屋流程、契約分析、租金補貼、帳號問題
- 每則問答可**上下移動調整顯示順序**(首/末項按鈕自動停用)
- 可單獨停用某則問答

#### 3. 法律文件
- 管理服務條款、隱私權政策等文件
- **每次儲存自動將版本號 +1** 並記錄更新時間
- 內容未變更時儲存鈕停用

#### 4. 輪播管理
- 管理儀表板 Banner:標題、圖片網址、連結網址、發布狀態
- 可**上下調整播放順序**
- 編輯時**即時預覽圖片**

### 連動點:公告與輪播上前台
**生效中的公告會自動顯示在兩處**:
- 使用者工作區 `/app` 儀表板(輪播下方)
- 使用者**通知中心**(與通知合併為單一收件匣,詳見模組四)

只有「已發布 + 已到開始日 + 未過結束日」三個條件同時成立才顯示。

**輪播**位於儀表板最上方,具備:自動輪播(5 秒)、左右切換箭頭、指示點、滑鼠移入暫停、點擊跳轉對應連結。僅顯示已發布項目,並依後台設定的順序播放。

> 儀表板由上而下的順序為:**輪播 → 公告 → 租屋總覽**。官網首頁 `/` 維持原本的行銷版面,不顯示公告與輪播。

### 技術核心
`isAnnouncementActive(公告, 現在時間)` 純函式(**7 個測試**),同時判斷發布狀態與生效區間。

## 四、模組三:RBAC 權限角色

### 解決的問題
原本只要是管理員就能存取全部後台功能,包含修改系統設定這類敏感操作,沒有分級控管。

### 功能

**三種管理員子角色**:超級管理員 / 營運管理員 / 內容審核員

#### 權限矩陣

| 頁面 | 超級管理員 | 營運管理員 | 內容審核員 |
|------|:---:|:---:|:---:|
| 後台總覽 | ✅ | ✅ | ✅ |
| 使用者管理 | ✅ | ✅ | — |
| 物件與評價審核 | ✅ | ✅ | ✅ |
| 訂閱與容量 | ✅ | ✅ | — |
| 內容管理 | ✅ | — | ✅ |
| 法規知識庫 | ✅ | — | ✅ |
| AI 品質監控 | ✅ | — | ✅ |
| 通知模板 | ✅ | — | ✅ |
| 稽核紀錄 | ✅ | ✅ | — |
| 系統設定 | ✅ | — | — |
| **可見頁面數** | **10** | **5** | **6** |

#### 側邊欄分群
從原本扁平的 9 個項目,重整為**三個有標題的群組**:
- **營運管理**:後台總覽、使用者管理、物件與評價審核、訂閱與容量
- **內容與知識**:內容管理、法規知識庫、AI 品質監控、通知模板
- **系統**:稽核紀錄、系統設定

群組內項目若全數無權限,**該群組整組不顯示**(例:內容審核員看不到「系統」群組)。

#### 角色指派
在「使用者管理」頁,管理員帳號那一列有下拉選單可直接指派權限角色;非管理員帳號顯示「—」。變更會寫入稽核紀錄。

### 雙重防護
1. **側邊欄隱藏** — 無權限的項目不顯示
2. **路由守衛攔截** — 直接輸入網址也會被擋下並導回後台總覽

兩層並行,不是只把入口藏起來而已。

### 技術核心
`canAdminAccessPath(角色, 路徑)` 純函式(**39 個測試**,逐格驗證權限矩陣)。未知路徑預設放行,避免誤擋既有功能。

## 五、模組四:通知模板 + 通知中心

### 解決的問題
專案原本**完全沒有通知系統**(僅有停水停電的個人偏好開關),平台無法主動通知使用者任何事情。

### 功能

#### 後台「通知模板」頁 — 分頁一:通知模板

模板欄位:
| 欄位 | 說明 |
|------|------|
| 名稱 | 模板識別名稱 |
| 分類 | 系統 / 租約 / 補貼 / 帳務 |
| 管道 | 站內 / Email / 推播(**可多選**) |
| 標題、內文 | 可嵌入變數 |
| 啟用狀態 | 可停用暫不使用的模板 |

**變數系統**
- 使用雙大括號語法標記動態欄位(例:到期日、姓名、金額)
- 編輯模板時**自動偵測並列出**該模板用到哪些變數
- **未填寫的變數會原樣保留**,不會變成空白 — 這樣漏填時一眼就能看出來

**發送流程**
1. 選擇模板 → 系統依偵測到的變數**動態產生對應輸入欄**
2. 填入變數值
3. 選擇收件人:全部使用者 / 全部租客 / 全部房東 / 指定單一使用者(管理員帳號自動排除)
4. **即時預覽**套用變數後的完整標題與內文
5. 送出後顯示實際送達人數

#### 後台「通知模板」頁 — 分頁二:發送紀錄
列出所有已送出的通知:收件人、標題、分類、管道、時間、已讀狀態。

#### 使用者端「通知中心」
位於側邊欄,是一個**合併收件匣**:同時顯示

| 來源 | 內容 | 標示 |
|------|------|------|
| **系統公告** | 內容管理發布、且在生效期間內的公告 | 「公告 · 等級」徽章,依等級著色 |
| **個人通知** | 管理員以模板發送給本人的通知 | 分類與管道徽章 |

兩者依時間新到舊**交錯排列**於同一份清單。

- **未讀以左側色條加粗體標示**(公告依等級呈現不同顏色),已讀樣式較淡
- 右上顯示未讀則數(公告與通知合計),可「全部標為已讀」
- 點擊單則即標記為已讀,狀態會保存

> 公告屬於廣播內容、本身沒有收件人,因此已讀狀態改以「使用者 → 已讀公告清單」另外記錄,**每位使用者各自獨立**,不會互相影響。

### 連動點
**後台送出 → 使用者立即在通知中心看到變數已套用的通知。** 實測發送給「全部使用者」得到 7 筆(10 位使用者扣除 3 位管理員)。

### 技術核心
- `extractVariables()` — 偵測模板使用了哪些變數
- `renderTemplate()` — 套用變數值(**16 個測試**)

兩個關鍵設計:
1. 未提供的變數保留原始標記,便於發現遺漏
2. 採用回呼式字串替換,確保變數值中含特殊符號時會照字面插入,不會被誤判為替換語法

## 六、共通架構

四個模組並非各自為政,而是套用同一套分層模式:

### 1. 純函式層(`src/utils/`)
商業邏輯抽離為不依賴框架的純函式,可獨立單元測試。這是 81 個測試的來源:

| 模組 | 純函式 | 測試數 |
|------|--------|:---:|
| 系統設定 | `validateSettings` | 16 |
| 內容管理 | `isAnnouncementActive` | 7 |
| RBAC | `canAdminAccessPath` | 39 |
| 通知模板 | `renderTemplate` / `extractVariables` | 16 |
| | **合計** | **81** |

### 2. 資料層(`src/composables/admin/`)
所有模組共用 `createAdminCollection()` 建立資料集合,統一負責:
- 自動讀寫 localStorage(重新整理不會遺失)
- 深層監聽,資料異動即時保存
- 模組級單例,不同頁面共享同一份狀態
- **跨分頁即時同步**:在後台分頁做的異動,會立即反映到另一個開著使用者頁面的分頁,無需重新整理

### 3. 稽核紀錄
**每一個異動操作都會寫入稽核紀錄**(誰、何時、對什麼、做了什麼),可在後台「稽核紀錄」頁查詢。

### 4. UI 層
四個模組共用同一組介面元件(對話框、下拉、表格、標籤),操作手感一致。

### 模組間的關聯
- 通知模板頁本身**受 RBAC 管控**(營運管理員看不到)
- 四個模組的操作紀錄**寫入同一份稽核紀錄**
- 內容管理的公告同時供應官網首頁與使用者儀表板

## 七、開發方法

本階段採用 **spec → plan → 分段實作** 的流程:

1. **設計文件(spec)** — 先釐清需求、比較做法、定義範圍界線,經確認後才動工
2. **實作計畫(plan)** — 拆成可獨立驗證的小任務,每個任務一個 commit
3. **測試優先(TDD)** — 核心邏輯先寫測試(確認失敗)再寫實作
4. **端到端驗證** — 不只看測試綠燈,每個模組都在瀏覽器實際操作驗證

相關文件位於 `docs/superpowers/specs/` 與 `docs/superpowers/plans/`。

## 八、目前範圍界線

以下項目本階段**未實作**,列出以利後續規劃:

- Email 與推播為**模擬**:僅記錄管道標記,未實際寄送或註冊推播服務
- 通知**無排程功能**,僅支援後台手動發送
- 側邊欄未做未讀數徽章(未讀數顯示於通知中心頁內)
- 資料存於瀏覽器 localStorage,尚未接後端資料庫
- 管理員子角色固定三種,無法自訂新增
